## 新発見

- **Edit は実行前に Read を伴う**: `Edit src/app.ts` 時、`Edit(src/**)` だけでなく `Read(src/**)` の
  `if` も評価・発火する。Edit 専用 hook を書いても同 path の Read 系 `if` が先に走る。doc に注記追加。
- 相対 glob (`src/**` / `out/**`) は **project dir 基準**で解決される (絶対 path ではない)。

## 適用余地レビュー (runbook §6 を新設してこのパスで初運用)

新 capability を理解したタイミングで「既存自作資産を簡単化/堅牢化/陳腐化させないか」を逆引きする
ステップを runbook に追加 (§6、旧仕上げは §7)。今回の候補:

- **Bash `if` のサブコマンド単位パース** → 既存 guard 系 plugin の自前 regex パースを補助できる可能性。
  `if: "Bash(git *)"` は `FOO=bar jj git push` の leading assignment 除去・`$()` 内判定を
  ランタイム側でやってくれるので、手製 regex の取りこぼし (= `$()`/leading var) や誤爆を減らせる。
  - 限界: guard は「マッチ後に repo owner 抽出/文面生成」もするので `if` は第1段フィルタ止まり
    (script 側パースは残る)。深いパターン `Bash(git push *)` は fail-open (guard では安全側)。

### 該当性確認の重要さ (= 部外者が的外れ issue を立てない)

候補を「guard 系 plugin」と一括りにしかけたが、起票前に各 hook の実体を読んで該当性を確認した:

| repo | hook の責務 | Bash `if` 該当? | 対応 |
|---|---|---|---|
| `claude-push-guard` | `git push`/`jj git push` の**コマンド名マッチ** | ✓ 該当 | 起票した |
| `claude-bash-safety` | double-quote 内 backtick の**クォート/内容解析** | ✗ 非該当 | 起票せず |
| draft `gh-issue-guard` | `gh issue create` の**コマンド名マッチ** | ✓ 該当 (未実装) | draft に考慮メモ追記 |

`if` の `Bash(...)` は「解析済みサブコマンド/path にマッチ」する機能で、**クォート解析は表現できない**。
bash-safety に提案するのは部外者の的外れ指示になるので回避 (= `dogfooding-feedback-upstream` の
「該当性を自分で確認してから起票」を実地で適用)。

### push-guard の自前 regex 誤爆を実地で踏んだ (= 起票の動機)

メンテ中に打った `grep -nE '...jj git push|git push|sed...' hooks/*.sh` が push-guard にブロックされた。
単一引用符内 regex の `|git push` を「パイプ後の git push」と誤認した false positive。文字列リテラルと
シェル構文を regex で区別できない例で、shell 構文解析する `if` なら避けられる。これを起票の実例に使った。
