## 前提バグ: `just check-freshness` が長期間 ERROR のまま動いていなかった

05de8cc (2026-06-18、バージョンマーカーのロックファイル化) で SKILL.md 冒頭のスタンプ行が `!`cat last-verified.txt`` の動的埋め込み構文になったが、justfile の `check-freshness` recipe は当時のまま SKILL.md への生 grep を続けていたため、それ以降ずっと `ERROR: SKILL.md の最終検証スタンプが見つかりません` で exit 1 していた。次の v2.1.177→v2.1.193 メンテパス (fedef8a、2026-06-26) でもこのバグは検出されず素通りしていた。今回 `last-verified.txt` を直接 grep するよう修正 (justfile 単体、fix commit)。**教訓**: 鮮度チェック自体が壊れていると「stale の検知漏れ」が起きる。メンテパス開始時に `just check-freshness` の exit code だけでなく出力内容も確認する習慣が要る。

## Workflow tool 運用上の発見: 巨大 `args` の値が subagent 側で `undefined` になった

triage agent の `promptPreview` を確認したところ、`args.repoRoot` / `args.changelogExcerpt` (114行) / `args.followupTodos` を埋め込んだ template literal 部分が文字列そのまま `"undefined"` として展開されていた (= `args` オブジェクトのプロパティが空だった)。原因未特定 (args の JSON サイズが大きい場合の Workflow tool 側の制限の可能性)。

**実害はほぼゼロだった**: triage agent の prompt 側に「まず runbook を Read」「CHANGELOG を確認」という指示文が残っていたため、agent が自律的に runbook (§2a/§2b の curl コマンド) と follow-up issue file を直接読みに行き、正しい CHANGELOG 内容で triage を完遂した。apply agent 側の `cd ${args.repoRoot}` も同様に `cd undefined` が失敗したはずだが、Workflow agent はデフォルトで呼び出し元セッションの cwd (= 当該リポ) を継承するため、実際のファイル編集は正しいパスに着地した (`git diff --stat` で確認)。

**次回への教訓**: 巨大なテキストを `args` 経由で渡すのはリスクがある。(a) agent 自身に一次資料を fetch/Read させる設計 (今回結果的にそうなった) の方が堅牢、(b) `args` を使うなら早期に `log(JSON.stringify(Object.keys(args)))` 等で着地確認するステップを workflow 冒頭に入れる、のいずれかを次回は明示的に採用する。

## 反証 / changelog と実機の食い違い

### 5 段 depth cap は「拒否」でなく「Agent tool の不可視化」で機能する

v2.1.174 時点の観測 (183 階層の単一チェーンが一度も spawn 拒否されず成立) は agents.md に反証として残っていたが、v2.1.181 の cap 修正後に再検証したところ解消した。ただし CHANGELOG が示唆する「5 段で拒否される」という素朴なイメージとは異なり、実際には depth=5 の子の環境で **`Agent` tool 自体が ToolSearch から見えなくなる** ことで cap が機能していた (= 明示的な block イベントではなくツールの不可視化)。

### CHANGELOG と公式 docs で stacked slash-skill invocation の上限数が食い違う (5 vs 6)

CHANGELOG v2.1.199 は「先頭 5 skill まで」とだけ書くが、公式 `commands.md` docs は「先頭 + 後続最大 5 個 (= 計 6 個)」と明記。どちらが正か実機確認しようとしたが、headless (`claude -p`) では機能そのものが再現せず (常に先頭 skill のみロード、対話 UI 前提の可能性)、確定できなかった。skills.md / builtin-slash-commands.md 両方に `[未検証: headless不可]` として明記。

### hooks.md 内の自己矛盾を発見・解消

旧 §7.2 は「SessionStart/SessionEnd/Notification は exit 2 で ignored」と一括りにしていたが、§10.3 では既に SessionStart/Notification を SessionEnd と分離して「stderr 表示のみ」と書いており矛盾していた。今回の実機検証 (v2.1.199 の stderr 可視化修正確認) が §10.3 側の記述が正しいことを裏付けたため、§7.2 を「SessionEnd/StopFailure = 完全 ignored」「SessionStart/Setup/SubagentStart = block不可・stderr表示」に修正して整合を取った。
